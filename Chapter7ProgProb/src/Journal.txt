For Phase 1, I got the core foundation of the Binary Search Tree up and running by building the BSTNode and BinarySearchTree classes,
and tested it all out with a dataset of accession IDs in Main.java. To get the insertion working smoothly,
I used a recursive helper method (recAdd) that compares any new ID against the current node using .compareTo().
If the value is smaller or equal, it navigates down the left subtree; if it's larger, it goes right. 
Once it hits an empty null spot, it drops in a brand-new node and uses clean re-linking to snap it into place as the stack unwinds.


The reason we have to bound our generic type with Comparable boils down to the fact that Java needs a universal way to evaluate relative sizes. 
Since our tree is generic and can handle different data types, requiring Comparable guarantees that whatever we store in it actually knows how to compare itself. 
That way, the tree can strictly enforce its core property, smaller values to the left, larger to the right, without running into errors.


For Phase 2, I added the height method to the BinarySearchTree class along with a private recursive helper called recHeight, and then updated Main.java to call archive.height() and print out the result. For our sample dataset, it successfully calculated a height of 2, which matches the expected level depth where the root starts at zero.

The height calculation works through recursion that checks every branch to find the longest one. When recHeight hits a null node, it returns negative one so that when the stack unwinds back to a leaf, the leaf's height becomes zero. As the recursion bubbles back up toward the root, it uses Math.max to compare the left and right subtree heights at each level, adds one to account for the current node, and ultimately passes the maximum depth of the deepest branch all the way back to the top.

For Phase 3, I implemented both the inOrderTraversal and preOrderTraversal methods inside the BinarySearchTree class, backed by private recursive helper methods, and then updated Main.java to call and display them with clear labels. The inorder traversal successfully printed all the accession IDs in ascending sorted order, while the preorder traversal visited the parent node first before moving down through its left and right subtrees, exactly matching the expected output for our sample dataset.

An inorder traversal naturally prints a binary search tree in sorted order because of how the BST property is structured. Since every node guarantees that all values in its left subtree are smaller or equal, and all values in its right subtree are larger, visiting the left child first ensures we always process the smallest available elements before touching the parent. Once the left side finishes, we print the current node's info, and then move on to the right subtree to handle the larger values, creating a completely sorted sequence from left to right across the entire tree structure.

For Phase 4 (Testing & Edge Cases), I ran our BST through a bunch of manual tests—including empty trees, single-node trees, balanced sample data, and a skewed sorted dataset. Testing the edge cases confirmed that our recursive base cases held up nicely: an empty tree returned a height of -1 without throwing any null pointer exceptions, and a single node accurately gave a height of 0.   

When inserting already-sorted data, every new node was larger than the last, forcing them all down the right branch and creating a completely skewed tree structure. This caused the height to scale linearly with the number of inserted items (height of $N-1$), basically turning our binary search tree into a glorified linked list. Compared to the balanced sample dataset where nodes split evenly down both sides to keep the height small, the skewed test showed how vulnerable un-self-balancing trees are to input order.
